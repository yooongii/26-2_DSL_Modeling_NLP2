## Project Overview

숙박 예약 페이지에서 가격·취소조건·추가비용은 한 화면에 모여 있지 않다. 취소조건은 팝업을 열어야 보이고, 추가비용은 설명란이 아니라 리뷰 곳곳에 흩어져 있고, 목록가와 실제 결제 총액도 다른 경우가 있다.

출발점은 **다크패턴(거짓 긴급성, 사전선택 등 위법 UI) 탐지**였다. 그런데 Agoda·Booking.com·Trip.com 실측 결과 명확한 위법 사례는 드물었고, 대신 **판단에 필요한 정보가 흩어져 있어 사용자가 직접 찾아 계산해야 하는 구조**가 반복적으로 나타났다. 그래서 다크패턴 탐지에서 **예약 판단 지원**으로 문제를 다시 정의했다.

| 축 | 담당 | 방식 |
|---|---|---|
| **Price Truth** | 실제 결제 총액 | 세금·수수료·추가인원 요금을 반영해 목록가 → 총액 계산 |
| **Terms IE** | 취소 시 손실 | 규칙 기반 파서로 취소조건 원문 → 날짜별 위약금 구간 구조화 |
| **Review IE** | 숨은 추가비용 | 공개 리뷰에서 비용 언급 문장을 규칙+모델 2단계로 판정 |

> **중간발표(2026-09 초)**: Agoda 단일 사이트, 한국어 리뷰만, 로컬 데모
> **최종(2026-10-01)**: Agoda·Trip.com·Booking.com 3사, 한국어·영어 동시 분석, Chrome 웹스토어 정식 배포(v1.1.0)

## Pipeline

```
아고다 · 트립닷컴 · 부킹닷컴
        │
  사이트 어댑터 (extension/sites.js, sites/*.js)
  각 사이트의 DOM에서 가격·취소조건·리뷰를 3사 공통 인터페이스로 읽기
        │
   ┌────┼──────────────┐
   │              │              │
Price Truth    Terms IE       Review IE
pricing.js     cancellation.js  reviewtab.js
세금·수수료·    정규식 파서 →    규칙 엔진(rules.ts) → 비용 키워드 문장 추출
추가인원 요금    lossSteps[]      → 분류 서버(모델) → 비용 신호 0/1
반영 → 총액     (D-day 구간별 %)      │
   │              │         Google Cloud Run (서울)
   │              │         문장만 전송 · 응답 후 즉시 폐기 · 요청당 ≤100문장
   └──────────────┴──────────────┘
                │
          briefing.js — 브리핑 카드
  예약 금액 · 취소 리스크 타임라인 · 추가비용 가능성 ·
  더 나은 옵션 · 숙소 저장 · 무료취소 마감 캘린더 등록
```

리뷰 판정은 역할을 분리했다. **유형**(주차·조식·보증금 등)은 키워드 규칙이 정하고, **모델**은 그 문장이 "진짜 비용을 말하는지"만 이진으로 판단한다. 유형 10종을 모델이 직접 분류하도록 먼저 시도했으나 9종이 F1 0.000대로 실패(`model-server/RESULTS.md` §2) — 임계값을 val에서 조정해도 1종(보증금, F1 0.727)만 복구됐다. 역할을 분리한 뒤에야 안정적인 성능이 나왔다.

**서버로 보내는 문장은 최대 50개로 제한한다.** 서버 응답 시간이 문장 수에 비례(40문장 ≈ 1.2초)하기 때문에, 리뷰가 많은 숙소라도 지연이 늘어나지 않게 상한을 두고 — 대신 "판정이 애매한 문장 → 최근 1년 리뷰 → 평점 낮은 리뷰" 순으로 우선순위를 매겨 값어치 있는 문장부터 모델에 보낸다(`review-engine/modelAnalyzer.ts`). 순위 밖으로 밀린 문장은 규칙 판정만으로 처리한다.

## Data

중간발표 때는 "리뷰 전문"을 학습 단위로 썼다. 최종은 "규칙 엔진이 추출한 비용 키워드 문장" 단위로 재수집·재라벨링했다.

| | 한국어 | 영어 |
|---|:---:|:---:|
| 문장 수 (train / val / test) | 982 (693 / 144 / 145) | 790 (555 / 118 / 117) |
| 키워드 포함 비율 | 100% | 88% |
| 양성률 | 67.6% | 64.6% |
| 사람 라벨 | 150건 (15%) | 132건 (17%) |
| LLM 라벨 | 832건 (85%) | 658건 (83%, 사람 검수 보정) |
| 분할 기준 | 숙소 단위 누수 검사 | 문장 중복 0건 |

라벨 기준: `1` = 돈이 실제로 오갔거나 확정(“유료주차라네요”) · `0` = 무료였거나 칭찬(“지하주차장도 무료”) · `?` = 문장만으로 판단 불가 → 채점 제외. LLM이 애매해하는 문장 위주로 282건을 직접 라벨링해 LLM 라벨을 보정하고 평가 골드셋으로 썼다.

## Model

| | 한국어 | 영어 |
|---|---|---|
| 베이스 모델 | `klue/roberta-small` | `distilbert-base-uncased` |
| 입력 | 규칙 엔진이 거른 후보 문장 1개 | 동일 |
| 출력 | 비용 신호 이진 확률 (유형 없음 — 유형은 규칙이 이미 가짐) | 동일 |
| 서빙 | Google Cloud Run (서울), `lang` 파라미터로 두 모델 서빙 | |

**서버 지연 최적화** — 문장 40개 기준 p50 응답시간 8.6초 → 1.2초:

| 단계 | 방법 | 결과 |
|---|---|---|
| 1 | 길이순 정렬 후 8개씩 배치(패딩 낭비 제거, 결과 동일) | 3.8초 |
| 2 | CPU 2 → 4 vCPU 증설 (사용 시간 과금 → 요청당 비용 차이 거의 없음) | 2.0~3.5초 |
| 3 | 한국어 모델 12층(base) → 6층(small) 교체, 정확도 유지(F1 0.860) | 1.2초 |

콜드스타트(최초 요청 약 23초)는 리뷰 수집 단계부터 서버를 미리 깨워 대응. 30초 안에 응답이 없으면 모델 판정 없이 규칙 판정으로 폴백.

## Output / Evaluation

### 최종 모델 성능 (베이스라인 대비)

| 구분 | 한국어 test 145 · Macro F1 / MCC | 한국어 사람라벨 36건 · F1 | 영어 test 117 · F1 | 영어 사람라벨 18건 · F1 |
|---|:---:|:---:|:---:|:---:|
| 전부 양성으로 예측 | 0.403 / 0.000 | — | — | — |
| 키워드 규칙만 | 0.643 / +0.317 | — | 0.609 | 0.533 |
| **최종 모델** | **0.860 / +0.726** | **0.750** | **0.911** | **0.870** |

클래스 비율이 균형적이지 않을 수 있어 Accuracy 대신 두 클래스를 균등 반영하는 Macro F1을 대표 지표로, MCC는 보조 지표로 확인.

### 자체 모델 vs LLM API

사람 라벨 중 학습에 쓰지 않은 71건으로 비교(프롬프트는 라벨링 가이드 그대로, temperature 0).

| | Macro F1 · MCC | 지연(p50, 40문장) | 페이지당 비용 | 데이터 반출 |
|---|:---:|:---:|:---:|:---:|
| **자체 모델** | 0.756 · +0.51 | **1.2s** | **$0**(한도 내) | 서울 리전 · 미저장 |
| gpt-4o-mini | 0.687 · +0.47 | 2.1s | $0.0003 | 미국 제3자 |
| claude-haiku-4.5 | 0.761 · +0.52 | 1.8s | $0.003 | 미국 제3자 |

사용자 1,000명(월 60만 페이지) 기준 월 비용 — 자체 모델 약 $100 vs Haiku 약 $1,900. 정확도는 Haiku와 대등, 비용·속도·데이터 통제는 자체 모델이 유리 → 최종 채택. (반대로 판정 기준이 바뀌면 LLM은 프롬프트 수정, 자체 모델은 재학습 필요 — 이 트레이드오프는 감수.)

### 추가비용 노출 규칙 — 모델 출력을 그대로 보여주지 않음

- 서로 다른 리뷰 **2건 이상**에서 같은 비용이 나올 때만 카드에 노출(단일 오판·중복 차단). 예: 힐튼 하와이안 빌리지 공개 리뷰 131건 → 한국어·영어 102건 분석 → 보증금·리조트피 각 2건 노출
- 페이지 표기와 3분류 대조: **표기와 충돌**(페이지엔 "무료 주차"인데 리뷰는 유료 — 1건이어도 노출) / **이미 안내된 비용**(페이지에 명시 — 숨은 비용 아님, 제외) / **표기 없음 + 2건 이상**(추가비용 가능성으로 노출)

### 알려진 한계

- 검증은 아직 소수 숙소·표본 중심(예: 위 힐튼 사례 1건). 다양한 숙소 유형 전반의 재현율은 미검증
- 사전에 없는 새 비용 표현은 규칙 엔진의 후보 문장 단계에서부터 제외 — 모델이 볼 기회 자체가 없음
- 가격 변동 추적(1~24시간 타임라인)은 미구현. Agoda가 반복적인 가격 수집(크롤링)을 차단 — 지금 보여주는 가격은 사용자가 이미 띄운 페이지의 DOM을 그 순간 읽는 것뿐, 별도 서버로 주기적 수집은 아님

## Usage

### 확장 프로그램 (로컬 개발용)
```
1. chrome://extensions → 개발자 모드
2. "압축해제된 확장 프로그램을 로드합니다" → extension/ 폴더 선택
3. 아고다 · 트립닷컴 · 부킹닷컴 숙소 상세 페이지 방문 — 브리핑 카드 자동 표시
```
리뷰 탭 판정은 배포된 Cloud Run 서버를 사용. 로컬 서버로 바꾸려면 `model-server/팀원-실행법.md`.

### review-engine 수정 반영
```bash
cd review-engine
# rules.ts / modelAnalyzer.ts 등 수정 후
node run.mjs bundle-ext     # extension/reviewtab.js 재생성
node run.mjs parity         # labeling/analyze.py와 같은 판정인지 검증
```

### 분류 서버 로컬 실행
```bash
cd model-server
pip install -r requirements.txt
python serve.py --model klue/roberta-small --binary --model-en distilbert-base-uncased
```
